# Freestanding Binaries

Okay before all this, what do I even mean by freestanding code?
Well, a good chunk of user space programs depend on their targets and the underlying OSes(This is also why you can't run a binary made for windows on a mac, because that binary was made with windows abstractions in mind).
This is because different OSes handle low level operations such as interfacing with the hardware differently and all platforms have their own interfaces.
This is also to mention the standard C library(more commonly referred to as THE standard library) which contains most of the fundamental code and abstractions
for each program.
If your operating system is the skyscraper, the standard library is the very useful plumbing and electricity in a way(i couldn't think of other essentials tbh)
It gives you a way to interact with the amenities of the skyscraper no matter what floor you're on.
And the userspace programs are kinda like the apartments/rooms within that skyscraper.
So we know, user space binaries to be actually executable require them to talk to the underlying OS and actually run
They don't execute directly on the CPU(well, YES THEY DO run on the CPU directly, but whenever they want to talk to the underlying hardware such as memory, disk or the screen, they have to ask the host OS kernel for permissions via system calls. And virtually a lot of operations fundamental to programming require interactions with these devices one way or the other
I mean obviously since it's again, running on the hardware.)

*But how is this a problem for us?*

Most modern programming languages and compilers ship with a stdlib and an existing operating system in mind
And well duh, programmers are gonna write code for pre existing platforms so to make it easier for everyone and make sure
that the programmer doesn't have to worry about dealing with the goofy interfaces themselves, they can simply start writing their own programs
and all the compliances and bureaucracy and interfacing bs can be handled by the standard library, the compiler and woah
You suddenly have an OS compliant binary? So cool right?

Referring back to the skyscraper analogy, think of the programmer as an apartment designer. They're working with pre-existing frameworks, the plumbing and wiring
all already done. All they have to do is build within an apartment and add their own vanities(or necessities) and now you have a great house!
(this is VASTLY oversimplified, user space programmers do a whole lot more and are working on higher abstraction layers that I myself don't
understand well enough. But again, for the purposes of this blog, this analogy should suffice)

Rust(the programming language we're gonna be using for this project) is also one such programming language

So our first goal would be to gain that bare metal hardware control...
But you might ask me how would we do that if we're using rust? a language heavily built upon pre-existing systems?

Well, that's exactly what we're gonna do today

Rust gives you the option to compile binaries that aren't dependent upon any os code or standard libraries, allowing us to use rust in its purest form as just
a way to express an extremely high level of assembly with abstractions and write our OWN code

### The deceptive nature of `fn main()` and `println!`

See, the thing is, main and the println! macro both rely on an existing operating system.
Main specifically, is kind of a lie. Normally, you'd be taught that this is the entry point for your program
and again, in most cases, as far as one would be concerned, it is true. Main really is the starting point for your program
But when you dig a little deeper into the binary, you'd find a symbol called _start(technically even this is a lie, the loader is the one which actually starts your program but again, I frankly don't know as much about that either)
this thing right here, is the actual entry point for the binary, and this contains a lot of setup code such that the program loads and exits properly
Now, I don't know about rust, but in C programming land, the _start routine contains a function call to a function named \_\_libc\_start\_main
with the pointer to our user defined main function as the first argument to it
and this \_\_libc\_start\_main function also has pretty important stuff which frankly, I really can't dive into for the scope of this project(YET, we will do something similar later down the line perhaps)

The println! function actually interacts with the hardware so much more than you'd expect.
Again, in C land, what the function takes is actually a pointer to a string(and string literals are in most cases hard coded strings which reside somewhere within the compiled binary)
So it would first need to take your string address, see if it has any format specifiers. It then has to copy it to memory. Now that's our first hurdle
memory management. How would your program just place something onto memory? And more importantly where? There are many MANY programs running on your computer, so how would the program know where to magically place the
new modified string in memory. Then, how will it send it over to the stdout so that it's readable output(we're not even talking about terminal emulators or ptys over here).
All of these are VERY interesting questions and problems that we ourselves would have to solve down the line. And this stuff highlights the importance of memory management, a kernel level allocator,
concepts such as memory paging. etc etc. we will cross that bridge when we get there though.
See, it's the little things that add up and make you realise how even the "trivial" parts of a user space program really relies on pre-existing infrastructure
so that it all works well.

### What the hell is Stack Unwinding
So while reading into the mechanics of rust(correction: reading phil-opp's blog), I found out that rust does something called stack unwinding
for error handling and then we dive a little deeper into the mechanics of [stack unwinding](https://www.bogotobogo.com/cplusplus/stackunwinding.php)...

**A small note on the stack**
Just from the wording itself, my guess as to what this is even about is how functions call and unload themselves.
See, whenever a function is called, it stores its context such as information about the function which called it, its arguments and its local variables
onto something called the callstack(or the program stack). Now, when a function call is executed from within an already existing function
the first thing that happens, is population of arguments(either via placing them into the register or pushing them onto the stack depending on calling conventions),
then saving the current state of the caller, jumping to the function and saving the current state of the stack(by pushing the base pointer of the stackframe of the caller function onto the stack).

Now that's a lot to take in but bear with me, can't functions that callers have called also call their own functions? Yes, yes they can. And for every function that
the program has called, there's a stackframe for the lifetime of that function. Therefore, when you're say, 4-6 function calls deep into a function
you first have to revert the stackframe into the n-1th depth of the function call(that is, the function which just called the function we're in right now).

How the heck does the stack even know how to revert back to the function which called it and hand over control back to the caller after our current function's job is done?

The answer to this lies in the saved state of the caller function. See, at the end of every function there are two specific instructions: `leave` and `ret`.
leave first of all destroys all the current context of the function such as local variables(or even the arguments pushed onto the stack in some ABIs) and then
restores the base pointer back to the frame of the caller function
and then ret uses the memory address pushed onto the stack by the caller and control is back in the hands of the caller.

And since we're what? 7 layers deep into the function, wouldn't every internal function have this routine? Yes, it would. So it's kind of like peeling layers
upon layers of the stackframe till we're back to the original caller function... kind of like an onion? Unwrapping in that sense would make a lot of sense.

**Well that's a guess on what stack unwinding is, but what's actually going on?**
Right, so rust is a high level programming language, it contains concepts of exceptions and destructors.
So remember that deep within the function calls concept we talked about earlier while exploring stackframes?
What would happen if something went wrong deep within that function call? Like an exception triggered and if this error isn't handled
correctly, then continuing code execution as is might lead to catastrophic results and state poisoning.
SO, in user land, in order to clear things up, first of all this deep recursion memory has to be discarded and the stack has to be cleared up right?
That's why, destructors for these deeply nested functions are called and stack memory is cleared up WITHOUT invoking any of the other code within
the functions themselves(and yes, this INCLUDES THE LEAVE AND RET, the stack cleanup is solely performed by the library that handles unwinding such as libunwind, so
the lifecycle of the stack we normally talk about doesn't count here. That isn't exactly why it's an exception but it's a helpful mnemonic/coincidence).
So, how do we know where the destructors are?

According to the linux standard, there's this section header in the ELF binary format called .eh_frame_hdr which basically contains the data for DWARF
based exception handling. Now what's DWARF? This is the standardised debugging format with ELF binaries in mind.

Now this is a bit of an interesting read, you can look into what [DWARF](https://en.wikipedia.org/wiki/DWARF) is, and how the [eh_frame_hdr is structured](https://refspecs.linuxfoundation.org/LSB_1.3.0/gLSB/gLSB/ehframehdr.html), maybe we might also have to implement our own exception handling
and stack unwinding. But as you can see, the sheer complexity and how deeply stack unwinding is tied to an underlying operating system handling these errors
and complying to these data structures is insane. In fact there's this library on linux systems called libunwind made specifically to deal with such things.
So yeah, we definitely do not need stack unwinding enabled for us.

So, in order to avoid such complicated semantics of error handling in the dawning of our very own OS, it is imperative we disable stack unwinding whenever
rust faces a panic condition. Thus, in cargo.toml:

```toml

[profile.dev]
panic = "abort"

[profile.release]
panic = "abort"
```

`__libc_start_main`

We talked about this earlier in the context of C runtimes and how main is kind of a lie.
Expanding upon that we see that:
For any standard system(be it windows, mac or linux), there exists a standard C library, with its C runtime.
ELF naturally would be linked against that library and the runtime would look for the \_start function
where within that runtime's \_start function, due to linking, `__libc_start_main` is the first thing that's
called after setting up the program's callstack and the registers.

This CRT and linking is again, very much operating system dependent, we don't want that runtime dependency in our binary though...

But one might question; we disabled the standard library via the no_std directive, we disabled the main function dependency via no_main
so why is cargo still crying about linker errors when we specifically told the rust compiler that we're not building with the standard library
or the main function?

This is because cargo(the build system which includes not only the compiler but also the linker and a lot of other steps), defaults to the native platform
we're building and using correct? So now, the next plan of action is to tell cargo to dissociate itself from the platform target and get us bare metal
architecture dependent(NOT platform dependent) build targets. This is usually done by something called target triples.

If you've ever built something like linux from scratch before, you'll remember that there were these goofy toolchains that we had to compile for our own OSes with
this particular format: `x86_64-lfs-linux-gnu`
See this here is a target triple. It tells you three* specific details to any compiler or binary or toolchain or WHATEVER what we're building for and where it's
supposed to run. x86_64 specifies the CPU architecture(obviously), lfs specifies the vendor and finally linux specifies the operating system/the underlying kernel.

\*(A slight note on this: Traditional target triples only had three fields - arch-vendor-os. Meanwhile, modern targets like the one mentioned here tack on
a fourth field for the ABI, even though everyone still stubbornly calls them 'triples'. For our freestanding kernel though, we don't have an OS ABI
let alone an OS for that matter. This is also why I didn't include "gnu" in the breakdown, it doesn't really matter that much for us)

You can also find yourself encountering something similar if you've used mingw64 on windows before, there were different targets from a selection of packages.

Now for a kernel, we don't have a specific target at all. All we have, is the CPU. The platform itself hasn't been defined, same with the standard C library.
Technically, these concepts don't really exist in this stage of the CPU's lifecycle, but high level programming languages due to ages of ecosystem
require these targets, and for good reason.

But for our purposes, we will only be dealing with architecture for now.

Right, so let's specify cargo to not use linux, windows, mac for the platform and not use any standard library like musl or glibc.
This can be done by telling cargo to build with the x86_64-unknown-none target(this is a stub target perfect for our usecase). But before all that, let's also
define our own start function within rust(again, courtesy to phil-opps)

```rs
#[unsafe(no_mangle)]
pub extern "C" fn _start() -> ! {
    loop {}
}
```

since i'm using the nightly build for rust and have rust-src installed, I can use these arguments to build my binary by directly compiling core
and use our specified target triple(you can check the flake.nix, it uses rust-overlay by oxalica)

```sh

```

I kinda diverged from phil-opp's guide here. The command above instructs cargo to NOT link against any runtime underneath whatsoever, making it clear

Now this totally isn't necessary but I got a little curious...

Why does a so called "freestanding binary" run from within an OS operating in userland?

We gotta first ask what our binary is doing in the first place. See as of now, whatever we told rust to do was just:
- don't use the standard library
- don't use the main entry point
- don't link against any start files when compiling
- disable OS dependent debug features

Right now, our binary just loops as soon as we tell it to start, it does nothing such as exiting or perform anything. It's literally just a stub/dummy.
Since our binary isn't exactly executing anything deep and just looping all over itself with basic architecture specific instructions
it should be perfectly legal for it to run... But why is it running without any of the specific "requirements" we talked about earlier
for our underlying operating system to actually run it?

You see, we're still compiling our binary down to a particular format called elf, and we can verify this by running the file command on our compiled binary:

```sh
[twilight@Nyxpad:~/dev/frosty/frosty/target/x86_64-unknown-none/debug]$ file ./frosty
./frosty: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), static-pie linked, with debug_info, not stripped
```
as you can see this is above this is an "ELF 64-bit LSB pie executable, x86-64".
That is, this binary is in the ELF format(which linux understands by default as its own executable format) and is also a binary that contains the machine code
for x86-64. The operating system specified is SYSV but we don't have an operating system associated with it. Well, as it turns out
the file command checks for a field called EI_OSABI within the ELF header. And whenever it's unset(or is left zero), the SYSV operating system is used as a
fallback name.

Let's check it ourselves though just in case:

```sh
[twilight@Nyxpad:~/dev/frosty/frosty/target/x86_64-unknown-none/debug]$ readelf -h ./frosty
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00 
  Class:                             ELF64
  Data:                              2's complement, little endian
  Version:                           1 (current)
  OS/ABI:                            UNIX - System V
```

and hexdump:

```sh
[twilight@Nyxpad:~/dev/frosty/frosty/target/x86_64-unknown-none/debug]$ xxd -l 16 ./frosty
00000000: 7f45 4c46 0201 0100 0000 0000 0000 0000  .ELF............
```

where:
- ELF magic: `7f45 4c46`(this is literally just "\x7fELF")
- EI_CLASS: `0x02`(this specifies ELF64)
- EI_DATA: `0x01`(this means little endian, two's complement)
- EI_VERSION: `0x01`(this specifies the current elf version)
- EI_OSABI: `0x00`(0x00 is just unspecified, now due to legacy purposes, it's interpreted as SystemV - the first commercial UNIX release that standardised the original ELF ABI)

Now, what exactly does the loader on linux distros do when we execute any file?
There's a system call within the linux kernel called `execve()`. And this isn't exactly dependent upon the stdlib or any of the start files
All it requires is the validation of the binary format(which is ELF - btw, execve syscall doesn't even care about the OSABI we talked about earlier), maps the segments of the program into memory and if it has
valid architectural code and no system calls, even a freestanding binary will run happily.
Of course, if we try to do anything privileged like we would do as a kernel, this binary would immediately do a segfault in userspace
