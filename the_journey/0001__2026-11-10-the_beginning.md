# Freestanding Binaries

Okay before all this, what do I even mean by platform independent code?
Well, a good chunk of user space programs depend on their targets and the underlying OSes(This is also why you can't run a binary made for windows on a mac, because that binary was made with windows abstractions in mind).
This is because different OSes handle low level operations such as interfacing with the hardware differently and all platforms have their own interfaces.
This is also to mention the standard C library(more commonly referred to as THE standard library) which contains most of the fundamental code and abstractions
for each program.
If your operating system is the skyscraper, the standard library is the very useful plumbing and electricity in a way(i couldn't think of other essentials tbh)
It gives you a way to interact with the ameneties of the skyscraper no matter what floor you're on.
And the userspace programs are kinda like the apartments/rooms within that skyscraper.
So we know, user space binaries to be actually executable require them to talk to the underlying OS and actually run
They don't execute directly on the CPU(well, YES THEY DO run on the CPU directly, but whenever they want to talk to the underlying hardware such as memory, disk or the screen, they have to ask the host OS kernel for permissions via system calls. And virtually a lot of operations fundamental to programming require interactions with these devices one way or the other
I mean obviously since it's agian, running on the hardware.)

*But how is this a problem for us?*

Most modern programming languages and compilers ship with a stdlib and an existing operating system in mind
And well duh, programmers are gonna write code for pre existing platforms so to make it easier for everyone and make sure
that the programmer doesn't have to worry about dealing with the goofy interfaces themselves, they can simply start writing their own programs
and all the compliances and bureaucracy and interfacing bs can be handled by the standard library, the compiler and woah
You suddenly have an OS compliant binary? So cool right?

Referring back to the skyscraper analogy, think of the programmer as an apartment designer. They're working with pre-existing frameworks, the plumbing and wiring
all already done. All they have to do is build within an apartment and add their own vanities(or necessities) and now you have a great house!
(this is VASTLY oversimplified, user space programmers do a whole lot more and are working on higher abstraction layers that I myself don't
understand well enough. But again, for the purposes of this blog, this analogy should suffice)

Rust(the programming language we're gonna be using for this project) is also one such programming language

So our first goal would be to gain that bare metal hardware control...
But you might ask me how would we do that if we're using rust? a language heavily built upon pre-existing systems?

Well, that's exactly what we're gonna do today

Rust gives you the option to compile binaries that aren't dependent upon any os code or standard libraries, allowing us to use rust in its purest form as just
a way to express an extremely high level of assembly with abstractions and write our OWN code

### The decpetive nature of `fn main()` and `println!`

See, the thing is, main and the println! macro both rely on an existing operating system
main specifically, is kind of a lie. Normally, you'd be taught that this is the entry point for your program
and again, in most cases, as far as one would be concerned, it is true. Main really is the starting point for your program
But when you dig a little deeper into the binary, you'd find a symbol called _start(technically even this is a lie, the loader is the one which actually starts your program but again, I frankly don't know as much about that either)
this thing right here, is the actual entry point for the binary, and this contains a lot of setup code such that the program loads and exits properly
Now, I don't know about rust, but in C programming land, the _start routine contains a function call to a function named \_\_libc\_start\_main
with the pointer to our user defined main function as the first argument to it
and this \_\_libc\_start\_main function also has pretty important stuff which frankly, I really can't dive into for the scope of this project(YET, we will do something similar later down the line perhaps)

the println! function actually interacts with the hardware so much more than you'd expect.
Again, in C land, what the function takes is actually a pointer to a string(and string literals are in most cases hard coded strings which reside somewhere within the compiled binary)
So it would first need to take your string address, see if it has any format specifiers. It then has to copy it to memory. Now that's our first hurdle
memory management. How would your program just place something onto memory? And more importantly where? There are many MANY programs running on your computer, so how would the program know where to magically place the
new modified string in memory. Then, how will it send it over to the stdout so that it's readable output(we're not even talking about terminal emulators or pttys over here).
See, it's the little things that add up and make you realise how even the "trivial" parts of a user space program really relies on pre-existing infrastructure
so that it all works well.

### How do we fix this problem then?
Now luckily, not all hope is lost. Rust does allow you to disable stadnard library and hand over all control to you.
Which is exactly what we need

there's an attribute called no_std which we can prepend to our program:

```
#![no_std]

fn main() {}
```

let's compile it:
